## 2. 产品定位

### 我们在市场中的位置

```
        功能多                      功能单一
           │                            │
    timeanddate.com                     │
    calculator.net                weeksuntil.com
           │                            │
           │                       ★ 我们在这里
           │                      （单一功能，极致体验）
           │                            │
           │                    各竞品的移动端
           │                    （臃肿、缓慢、广告多）
           │
    功能多 + 体验差              功能少 + 体验好
```

### 定位声明

| 维度 | 描述 |
|---|---|
| **目标用户** | 用 Google 搜索日期问题的普通人（非专业用户） |
| **市场** | 全球英语用户，移动端为主 |
| **核心利益** | 打开页面即获答案，比任何竞品快 3 倍 |
| **支持理由** | 极简页面 + 无广告 + 每个页面精确匹配一个搜索意图 |
| **竞争锚点** | timeanddate.com 是功能最全的，我们是长尾体验最好的 |

### 我们不是什么

- ❌ 我们不是 "下一个 timeanddate.com"
- ❌ 我们不是通用计算器平台
- ❌ 我们不是日历应用
- ❌ 我们不是内容站

**我们是：长尾日期查询的即时答案引擎。**

## 3. 为什么用户选择我们

| 用户动机 | 竞品现状 | 我们做到 |
|---|---|---|
| "我想快点知道答案" | 打开页面 → 看到广告 → 找日期选择器 → 点两次日历 → 点计算 → 等结果 | 打开页面 → 答案在首屏正中间 |
| "我在手机上搜的" | 日历选择器太小，经常点错 | 页面不做复杂交互，直接展示答案 |
| "我只想知道天数" | 竞品给你天数、周数、月数、年数、时区差……信息过载 | 大字显示天数，其他信息放在下方 |
| "我不喜欢广告" | 竞品 3-5 个广告位置 | MVP 阶段零广告 |
| "我每年都搜这个词" | 每年看到同一个通用页面 | 每年都有一个专门的、更新的页面 |

## 4. 为什么 Google 应该推荐我们

Google 的排名因素中，我们能赢的地方：

| Google 关注点 | 我们的优势 |
|---|---|
| **Core Web Vitals（LCP/FID/CLS）** | 纯静态 HTML，LCP < 1.5s，FID = 0，CLS = 0 |
| **内容相关性** | 每个页面 title/h1/内容精确匹配一个查询 |
| **结构化数据** | Schema.org WebApplication / FAQPage / BreadcrumbList 标记让搜索结果更丰富 |
| **移动优先** | 所有页面按移动端设计，桌面端兼容 |
| **HTTPS** | Vercel 自带 HTTPS |
| **域名权威（长期）** | 工具站天然吸引 backlink（开发者推荐、Reddit 引用、博客链接） |
| **新鲜度** | 通过 Vercel Deploy Hook 每周自动重建，保持倒计时和推算页面新鲜 |

### 我们不会被 Google 惩罚，因为：

- ✅ 每个页面提供真实计算价值，不是 AI 生成的垃圾内容
- ✅ 页面之间有实质差异（不同日期、不同事件），不是 duplicate content
- ✅ 结构化数据帮 Google 理解页面内容
- ✅ 用户行为信号好（快速加载 → 低跳出 → 高满意度）

## 5. MVP 范围

### MVP 包含的功能（P0）

```
📅 功能 1：Days Between Two Dates
   - 一个交互式计算器页面（工具页）
   - 用户可输入两个日期，得到天数
   程序化页面：
   - "Days between [Date1] and [Date2]" 精选组合 ~100 页
   - "How many days since [Event/Date]" ~50 页

📅 功能 2：Date From Today
   - 交互式计算器页面
   程序化页面：
   - "[N] days from today" ~30 页（常见 N 值）
   - "[N] days from [Date]" ~200 页（精选组合）

📅 功能 3：Event Countdown
   程序化页面：
   - "How many days until [Event] [Year]" ~150 页
   - 覆盖 50 个全球节日 × 3 年

📅 功能 4：Month/Year Info
   程序化页面：
   - "How many days in [Month]" ~12 页
   - "How many days in [Year]" ~7 页
   - "Days left in [Year]" ~3 页

📅 功能 5：Age in Days
   程序化页面：
   - "How many days old am I" ~1 页（交互式）
   - "Age in days for birth year [Year]" ~20 页
```

### MVP 总页面量：~600 页

### 每页必须包含

```
✅ 大字答案（核心数据）
✅ 清晰标题（H1，匹配搜索意图）
✅ 辅助信息（星期、周数、上下文）
✅ Schema.org 结构化数据
✅ 面包屑导航
✅ 日期间的解释性文字（1-2 句，对 SEO 有用）
✅ 内部链接（到相关计算页面）
✅ Canonical URL
✅ Open Graph tags
```

## 6. 暂时不做什么

### MVP 不做

| 项目 | 原因 |
|---|---|
| ❌ 工作日计算 | 各国假期差异大，配置复杂 |
| ❌ 时区转换 | 需要时区数据库，维护成本高 |
| ❌ 周数差 / 月数差 | 先专注天数，验证假设后再扩展 |
| ❌ 用户输入交互页面 | 先靠搜索流量验证需求，交互页面后续补 |
| ❌ 注册 / 登录 | 工具站不需要 |
| ❌ 收藏功能 | 不是 MVP 核心 |
| ❌ 广告 | 先积累用户信任和排名 |
| ❌ 多语言 | 先只做英语 |
| ❌ 移动 App | 先做好 Web |
| ❌ API 服务 | 等有流量再考虑 |
| ❌ 日历/日程功能 | 不是工具范畴 |

### 永远不做（原则性）

| 项目 | 原因 |
|---|---|
| ❌ AI 生成的内容 | 日期计算是确定性算法，不需要 AI。用 AI 生成文案 = 低质量 = Google 不收录 |
| ❌ 购买 backlink | 短视行为，Google 会惩罚 |
| ❌ 内容农场策略 | 我们每个页面都有真实计算价值，不是为 SEO 而 SEO 的空壳页面 |
| ❌ 弹窗广告 / 遮挡式广告 | 毁体验 = 毁排名 |
| ❌ 用户数据收集 / 售卖 | 信任一旦失去就回不来 |

## 9. 长期愿景（MVP 之后）

如果 MVP 验证成功（6 个月内日点击 > 500）：

```
Phase 2: 扩展日期对页面到万级
Phase 3: 增加工作日计算
Phase 4: 增加周数 / 月数计算
Phase 5: 扩展到其他计算品类（时间、单位等）
Phase 6: 考虑极轻量的变现（单条 Carbon Ads）
```

如果 MVP 失败（6 个月内收录 < 30% 或日点击 < 50）：

```
→ 诊断原因（技术问题？关键词选择错误？）
→ 决定是 pivot 还是终止
→ 技术栈保留，转向其他 Programmatic SEO 品类
```
